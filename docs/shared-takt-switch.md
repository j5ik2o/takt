# 共有 TAKT の切替手順

フォークの共有 TAKT（`~/local/takt-custom`）を新しいビルドへ切り替えるときの運用手順です。本家に提案する内容ではありません。

この文書は手順の記録です。書いた時点では、共有のパス・設定・プロセスに対してどのコマンドも実行していません。

## 配置の形

- 実体は版ごとのディレクトリに置きます。名前は `~/local/takt-custom-<コミットの短縮SHA>` です（例: `~/local/takt-custom-f6c0d505`）。
- `~/local/takt-custom` は、使用中の版を指すシンボリックリンクです。利用者はこのリンク経由で `takt` を起動します。
- 切替は、新しい版のディレクトリを置いてからリンクの向き先を変える操作です。既存の版のディレクトリは上書きしません。
- この手順は、`~/local/takt-custom` がすでにリンクになっていることを前提にします。実ディレクトリのままの場合、手順 5 の `ln -sfn` はそのディレクトリの中にリンクを作ってしまいます。先に実ディレクトリを版別の名前へ移してから、リンクを作ります。

## 切替の前に知っておくこと

`takt manager`、`takt director`、`takt-mcp` は、起動した時点のプログラムを読み込んだまま動き続けます。リンクを切り替えても、起動済みのものは新しい版になりません。以下では、この3つをまとめて「常駐するコマンド」と呼びます。`takt-mcp` には、MCP クライアントが子プロセスとして起動したものと、`takt-mcp --http` で常駐させたものの両方を含みます。`takt-mcp` は、ゴールの再開時と、登録案の承認・取り下げ時に daemon へ接続します。

daemon を必要とするコマンドは、起動中の daemon を次のように扱います。

| 起動中の daemon | 扱い |
|---|---|
| バージョンが同じで、daemon が起動時に記録した実パスが、コマンドのパスの今の実体と同じ（リンク経由と実パスの違いだけ） | そのまま接続する。PID は変わらない |
| バージョンが同じで、別の版のディレクトリから起動されている | `SIGTERM` で止め、自分の版の daemon を起動する |
| バージョンが違う | `SIGTERM` で止め、自分の版の daemon を起動する |

コマンド自身のプログラムファイルが見つからない場合（版のディレクトリを消した後など）の扱いは、起動中の daemon によって変わります。バージョンが同じでパスの文字列が違う daemon は、止めずにエラーで終わります。自分の daemon を起動できないコマンドが、動いている daemon を止めないためです。バージョンが違う daemon は、この確認より先に止めます。その後の起動に失敗するので、daemon は止まったままになります。版のディレクトリは、そこから起動したコマンドをすべて終了してから消します。

このため、古い版から起動した常駐するコマンドが残ったまま新しい版のものを起動すると、両者が互いの daemon を交互に止めます。切替では、古い版の常駐するコマンドを先にすべて終了します。

同じファイルかどうかは、接続するたびに判定します。daemon 側は起動時に記録したパスをそのまま使い、コマンド側のパスだけをその時点のリンクの向き先で解決します。daemon が動いている間にその場所が別の版へのリンクに置き換わっても、古い daemon を新しい版と取り違えません。その代わり、実ディレクトリだった時期のパスを記録している daemon は、中身が同じファイルのままでも、実パスで起動したコマンドが最初に接続したときに一度だけ入れ替わります。

コマンド側には取り違えが残ります。パスをリンクの文字列で覚えているコマンドは、リンクが新しい版へ切り替わると、バージョンが同じなら、新しい版の daemon を自分の配置とみなして接続します。古い版の daemon が動いていればそれを止め、daemon がなければリンク経由で新しい版の daemon を起動します。どちらの場合も、コマンド自身は古い版のプログラムのままです。パスをリンクの文字列で覚えるのは、通常は、その場所が実ディレクトリだったときに起動し、後からリンクに置き換えられた場合だけです。これも、古い版の常駐するコマンドを先に終了する理由です。

2026-11-24 の切替では、この扱いに不具合がありました（[#110](https://github.com/j5ik2o/takt/issues/110)）。切替前から動いていた manager が `~/local/takt-custom/...` という文字列で daemon のパスを覚えており、daemon が記録した実パス `~/local/takt-custom-f6c0d505/...` と文字列が違うだけで daemon を止め続けました。#110 の修正を含む版では、コマンドのパスがリンクで、daemon の記録がそのリンク先の実パスなら、同じ配置として扱います。修正を含まない版から起動した常駐するコマンドには修正が効かないので、終了させる必要があります。

## 手順

実行中の作業がない短い時間帯に行います。`<新>` は新しい版の短縮SHA、`<旧>` は切替前の版の短縮SHAです。設定ディレクトリを `TAKT_CONFIG_DIR` で変えている場合は、以下の `~/.takt` をその場所に読み替えます。

1. **実行中の作業がないことを確認する。** 実行中のゴールやタスクがあれば、終わるのを待ちます。現在の daemon は次で確認し、PID・`version`・`cliPath` を控えます。

   ```sh
   cat ~/.takt/daemon.json
   readlink ~/local/takt-custom    # 戻すときに使うので控える
   ```

2. **古い版の常駐するコマンドをすべて終了する。** 開いている `takt manager` と `takt director` の画面をすべて閉じます。`takt-mcp` は、起動元の MCP クライアントを終了するか、`takt-mcp --http` のプロセスを止めます。残っていないことを確認します。

   ```sh
   pgrep -fl 'takt.*(manager|director)|takt-mcp|app/mcp/index\.js'
   ```

   この検索は、コマンドラインに `takt` と `manager` を含むだけの無関係なプロセス（takt のチェックアウトで開いたエディタなど）も拾います。数えるのは `takt` と `takt-mcp` の実行だけです。Linux では `-l` がプロセス名しか出さないので、`pgrep -fa` を使います。

3. **古い daemon を止める。** 古い版のまま止めます。止まると `daemon.json` がなくなります。

   ```sh
   takt daemon stop
   cat ~/.takt/daemon.json         # No such file であること
   ```

4. **新しい版を配置する。** ビルドした一式を `~/local/takt-custom-<新>` に置きます。`~/local/takt-custom-<旧>` は残します。

5. **リンクを切り替える。**

   ```sh
   ln -sfn takt-custom-<新> ~/local/takt-custom
   readlink ~/local/takt-custom    # takt-custom-<新> であること
   ```

6. **新しい版の manager を起動する。** `takt manager` を起動します。daemon は manager が自動で起動します。止めていた `takt-mcp` もここで起動し直します。

7. **PID を照合する。** `cliPath` が新しい版のディレクトリを指し、その PID のプロセスが動いていることを確認します。

   ```sh
   cat ~/.takt/daemon.json         # cliPath が ~/local/takt-custom-<新>/dist/app/daemon/index.js
   ps -p <daemon.json の pid> -o pid,lstart,command
   ```

   続けて manager をもう1つ起動し、`daemon.json` の `pid` が変わらないことを確認します。変わる場合は、古い版から起動した manager、director、`takt-mcp` のどれかが残っています。手順 2 に戻ります。PID が変わらなくても、残った古いコマンドがまだ daemon に接続していないだけのことがあります。残っていないことの確認は、手順 2 の検索で行います。

## 戻し方

新しい版で問題が出たら、同じ流れで向き先だけを戻します。

1. 手順 2 と同じ方法で常駐するコマンドをすべて終了し、`takt daemon stop` で daemon を止めます。
2. 手順 1 で控えた向き先へリンクを戻します。

   ```sh
   ln -sfn takt-custom-<旧> ~/local/takt-custom
   ```

3. `takt manager` を起動し、手順 7 と同じ方法で `cliPath` が `~/local/takt-custom-<旧>` を指すことと PID を確認します。

`~/local/takt-custom-<旧>` は、新しい版の動作を確認し終えるまで消しません。

## 終了フックを含む版へ切り替えるとき

タスク終了フック（`task_finish_hook`。[設定の説明](configuration.ja.md#タスク終了フック)）を含む版への切替も、上の手順のまま行います。この節は、その切替に固有の点だけをまとめます。

- **切替だけでは何も変わりません。** フックは、プロジェクトの `.takt/config.yaml` に `task_finish_hook` を書いたプロジェクトでだけ動きます。書いていないプロジェクトの動作は、切替前と同じです。
- **古い版は `task_finish_hook` を知りません。** 古い版はこのキーを設定の誤りとして扱い、そのプロジェクトの設定を読めなくなります。キーを書くのは、手順 7 で新しい版の daemon を確認した後にします。先に書かないでください。
- **設定は、タスクが終わるたびに読みます。** キーを書いた後に終わるタスクから効きます。manager や daemon の起動し直しは要りません。動いている実行を止める必要もありません。
- **コマンドには `HOME` や認証情報を渡しません。** 渡すのは `PATH` などの少数の変数と `TAKT_FINISH_*` だけです。通知に `HOME` や鍵が要るコマンドは、コマンドの中で設定します。
- **コマンドの実行中は実行枠を使います。** コマンドが止まると、タスク1件ごとに最大で `timeout_ms`（上限60秒）と1秒ほど、その枠の次のタスクが遅れます。最初は `timeout_ms` を短く（既定の10秒以下）にします。

### 有効にする

1. 手順 1〜7 で新しい版へ切り替え、`daemon.json` の `cliPath` が新しい版を指すことを確認します。
2. 対象のプロジェクトの `.takt/config.yaml` に書きます。コマンドは絶対パスで書きます。

   ```yaml
   task_finish_hook:
     command: [/絶対パス/notify-task]
     timeout_ms: 5000
   ```

3. 次に終わったタスクで、コマンドが1回だけ呼ばれたことを、コマンド側の記録で確認します。`takt list` の状態が、フックを書く前と同じ形で保存されていることも確認します。

### 戻し方

- **フックだけを止める。** `.takt/config.yaml` から `task_finish_hook` を消します。次に終わるタスクから呼ばれなくなります。起動し直しは要りません。保存済みのタスクの状態は、フックの有無で変わらないので、直すものはありません。
- **版ごと戻す。** 先に、`task_finish_hook` を書いたすべてのプロジェクトからこのキーを消します。残したまま古い版へ戻すと、古い版がそのプロジェクトの設定を読めません。その後、上の「戻し方」の手順でリンクを戻します。

## プロジェクトで共有 TAKT を使うように固定する

mise で npm の takt（例: 0.77.0）を入れていると、`PATH` の `takt` はそちらになります。上流の版は、フォークにしかない設定キー（`task_finish_hook` など）を知りません。そのキーを書いたプロジェクトでは、`takt` が次のエラーで止まります。

```text
Configuration error: invalid (root) in <project>/.takt/config.yaml: Unrecognized key: "task_finish_hook"
```

フォークの版は、このエラーの後ろに `takt <版> does not support key "task_finish_hook"` と、動いている版を付けて出します。上流の版の文言は変わりません。

フォークのキーを使うプロジェクトでは、そのプロジェクトの中でだけ `takt` が共有 TAKT（`~/local/takt-custom`）を指すようにします。mise の npm の takt は消さず、ほかのプロジェクトではそのまま使います。

### mise.toml の書き方

プロジェクトの根に `mise.toml` を置き、`PATH` の先頭に共有 TAKT の `bin` を足します。

```toml
[env]
_.path = ["{{env.HOME}}/local/takt-custom/bin"]
```

初めて置いたときは、そのディレクトリで `mise trust` を実行します。

- **`mise activate` で `PATH` を作るシェルでだけ効きます。** `_.path` は mise が組み立てる `PATH` の先頭に入り、npm の takt より先に見つかります。`mise exec -- takt ...` でも同じです。
- **shims だけを `PATH` に入れているシェルでは効きません。** `~/.local/share/mise/shims/takt` は npm の takt の shim で、`_.path` があっても npm の takt を起動します。エージェントや CI のシェルはこの形のことがあります。そのため、次の確認を run の前に行います。
- **リンクを指します。** `_.path` には版ごとのディレクトリではなく `~/local/takt-custom/bin` を書きます。切替でリンクの向き先が変わると、プロジェクトの設定を変えずに新しい版になります。

### run の前の確認

`scripts/check-takt-runtime.sh` で、次の3つを確かめます。どれかが合わないと `NG:` の行を出し、終了コード 1 で終わります。

1. `command -v takt` が、リンクを解決した後で `~/local/takt-custom/bin/takt` と同じファイルを指すこと。
2. 共有 TAKT のビルドが、プロジェクトの使う設定キーを知っていること（`dist/core/models/config-schemas.js` にそのキーがあること）。キーは `--key` で指定し、繰り返して複数指定できます。省略すると `task_finish_hook` を調べます。
3. `DEPLOYED_FROM_COMMIT` が、版のディレクトリ名（`takt-custom-<短縮SHA>`）と合うこと。`--repo <フォークのチェックアウト> --contains <コミット>` を付けると、配置した版がそのコミットを含むことも確かめます。

```sh
# プロジェクトのディレクトリで実行する
/path/to/takt/scripts/check-takt-runtime.sh --key task_finish_hook
# 終了フックのコミットを含むことも確かめる
/path/to/takt/scripts/check-takt-runtime.sh --repo /path/to/takt --contains b1acb58ac
```

`takt --version` では見分けられません。フォークの版は、元にした上流の版番号（例: `0.76.1`）をそのまま名乗ります。

共有 TAKT の場所が違うときは `--root <ディレクトリ>` で渡します。

### 共有 TAKT を更新したとき

新しい版への切替は、上の「手順」のとおり版のディレクトリを作ってリンクを張り替えます。プロジェクトの `mise.toml` は変えません。張り替えた後、キーを使う各プロジェクトで `check-takt-runtime.sh` を実行し、3つとも `ok:` になることを確かめます。新しい版が、プロジェクトの使うキーを持たないことがあります（そのキーを足す前のコミットから作った版など）。その場合は 2 番目の確認が `NG:` になるので、キーを持つ版へ戻します。
